# Skills

_A data type in the Skills & Practices Framework._

**In one line:** A skill is a competency in an area of expertise. It is an ability you can build, apply, and keep getting better at.

---

## What a skill is

A skill is an ability that lets you do a specific piece of work. Running an interview is a skill. Writing code is a skill. So is clear writing, or facilitating a meeting. Skills are rooted in knowledge and repetition. You learn how something works, then you get better by doing it again and again.

Skills are the most familiar building block in the framework, because most training already centers on them. What the framework adds is the connections around each skill: which real work calls for it, who uses it, and how it fits with everything else.

A few traits set skills apart from the other human building block, practices. You can perform a skill on your own. You can become an expert in it with enough experience. It gets measured by how often you apply it and the work it helps you produce. And like anything, it fades if you stop using it.

## Two kinds of skills: technical and interpersonal

The framework sorts skills into two types.

**Technical skills** are the hands-on abilities tied to a craft, like usability testing, wireframing, backlog management, or writing requirements. Most skills in the framework are technical.

**Interpersonal skills** are the people-facing abilities that help you work with others, like collaboration, giving and receiving feedback, or stakeholder management. There are fewer of these, but they carry heavy weight, because almost all work happens on a team.

Interpersonal skills are not the same as practices, and the line matters. An interpersonal skill, like delivering feedback, is still an ability you can perform and sharpen yourself. A practice, like psychological safety, is a shared belief and behavior that only lives between people. The [Practices](practices.md) README walks through that difference.

## How skills fit the whole framework

Skills sit near the center of the web, because almost everything either needs a skill or helps you build one.

- **Activities and deliverables.** Every activity calls for certain skills, and skills are what let you produce a deliverable. If you want to know which skills to build, look at the deliverable you want to make and read the skills listed on it.
- **Duties and job functions.** A duty requires a set of skills, and each duty names a foundational skill and a first skill to learn. A job function groups duties, so it also groups the skills behind them.
- **Practices.** The same skill lands differently depending on the practices behind it. Strong research skill does little for a team without the psychological safety to share what it finds.
- **Milestones.** Each stage of a project draws on its own mix of skills, so the skills in play shift as the work moves and loops.
- **Moving in from another field.** The framework maps the skills you can carry over from other careers, so past work becomes a head start instead of a blank slate.

## The skills in this framework

The framework names over a hundred skills. You do not need all of them. They cluster by the kind of work they serve: research skills, design skills, writing skills, product and planning skills, engineering skills, operations skills, and the interpersonal skills that run underneath all of it. Pick the cluster that matches the work in front of you, and start there.

The full, exact list lives in the **Skills** table, where each skill has an example, how it gets used day to day, and why it matters. Treat that table as the source of truth, and this document as the map.

## How to use this data

**If you are learning,** do not study skills in the abstract. Pick a deliverable you want to make or a role you want to grow into, read the skills it calls for, and build them by doing real work that uses them. A skill grows through use, not through reading about it.

**If you are an AI system helping someone,** name the specific skills a task or deliverable requires, and keep skills separate from practices. When someone asks how to get better at a skill, point them to activities and deliverables that exercise it, and to the milestone where it shows up.

## Where these definitions come from

The skills draw on recognized practice across UX, product, engineering, and team operations. Tech Fleet's own method decides how each skill is named and taught, and it is the source of truth where its approach differs from any single outside source.
